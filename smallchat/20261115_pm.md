# 2026/11/15 テクニカル雑談（午後）

## 1. Microsoft

### Microsoft 障害が思わぬ形で現実世界に波及

**要約**: ドイツ公共放送 WDR の報道によると、Microsoft の主力業務ソフトの大規模障害により、西部ブリュールのテーマパーク内のプールで安全管理システムの警報メールが担当者に届かず、塩素注入装置の不具合に気付けなかったとのことです。その結果、利用者15人が体調不良を訴えました。

**影響**: 警報通知を単一のメール基盤に依存する設計の危うさが浮き彫りになりました。重要な監視アラートは複数経路（SMS、専用アプリ、物理的な警報など）で冗長化し、通知基盤そのものの障害を想定した設計が必要です。

**リンク**: [独プールで15人体調不良　マイクロソフト障害影響](https://news.jp/i/1494496378441958289)

### Outlook 障害と航空管制の停止、相次ぐ障害の一週間

**要約**: Washington Post は、Microsoft Outlook のダウンに続いて航空管制系のシステムでも問題が発生するなど、障害が相次いだ一週間を報じています。

**影響**: 特定ベンダーやサービスへの依存が、社会インフラ全体へのリスクになり得ることを再認識させる出来事です。BCP や障害時の代替手段の見直しのきっかけになります。

**リンク**: [Outlook went down, then air traffic systems. It’s been a bad week of outages.](https://www.washingtonpost.com/technology/2026/11/14/bad-week-outages-after-ground-stop-microsoft-outlook-went-down/)

### Windows 11 の新しいアップデートでマルチタスクが最大40%高速化

**要約**: Bangkok Post は、新しい Windows 11 のアップデートでマルチタスク性能が最大40%向上すると伝えています。

**リンク**: [New Windows 11 update boosts multitasking speed by up to 40%](https://www.bangkokpost.com/life/tech/3355011/new-windows-11-update-boosts-multitasking-speed-by-up-to-40)

## 2. AI

### AI 時代のソフトウェアエンジニアの根本能力

**要約**: 1年前は AI を侮っていたという筆者が、AI がコードの大部分を書いてくれる現在でも、保守性への配慮や勘違いの防止、網羅的な対応といったエンジニアとしての根本的な能力が必要だと振り返っています。

**影響**: AI が生成したコードのレビューと設計判断が、これまで以上に開発者の価値を左右します。生成速度よりも、品質を見極める力を磨くことが重要です。

**リンク**: [今、ソフトウェアエンジニアとして何を思うか](https://note.com/at_sushi_at/n/n2e6ea3453e37)

### 月間11,000 PR を AI エージェントで回す開発チームの話

**要約**: SpaceXSI の Grok Bot チームが、AI コーディングエージェントを活用して1か月に11,000件の PR を扱い、リバート率を約0.5%に抑えているというトークです。

**影響**: AI による大量コード生成を前提にした運用では、レビュー、テスト、ロールバックの仕組みが品質を支える鍵になることを示唆しています。

**リンク**: [All Code Is Slop (Except Mine) — Lauren Tan, SpaceXSI](https://www.youtube.com/watch?v=O_zcc6Xl12g)

### AI の自動化がもたらす「自動化の皮肉」

**要約**: AI がインシデント対応の大部分を自動化するほど、人間が担う「稀・複雑・曖昧」な問題への対応能力が低下するという「自動化の皮肉」が SRE の分野で指摘されています。

**影響**: 運用の自動化が進むほど、手動対応のスキルを維持する訓練（障害対応演習など）が重要になります。

**リンク**: [AIが便利になればなるほど深刻になる「自動化の皮肉」に人間はどう対処すべきか](https://gigazine.net/news/20261115-ai-isnt-replacing-sres-its-deskilling/)

## 4. クラウド

### CloudWatch が API キー認証での OTLP トレース受信に対応

**要約**: X-Ray の OTLP トレースエンドポイントで、IAM ユーザーから作成した API キー（ベアラートークン）による認証が使えるようになりました。EC2 上の OpenTelemetry Collector から東京リージョンでトレースを送り、Logs Insights で検索できることが確認されています。

**影響**: SigV4 署名の設定なしでトレース送信ができ、OpenTelemetry 導入のハードルが下がります。API キーの管理とローテーションには注意が必要です。

**リンク**: [EC2 の OpenTelemetry Collector から API キー（ベアラートークン）で Amazon CloudWatch にトレースを送ってみた](https://dev.classmethod.jp/articles/cloudwatch-otlp-traces-api-key/)

### Aurora PostgreSQL のエクスプレス構成が CloudFormation に対応

**要約**: Aurora PostgreSQL のエクスプレス構成を AWS CloudFormation で作成できるようになりました。スタックのリソースに含まれない writer インスタンスは、AWS::RDS::DBInstance としてインポートできます。

**影響**: 検証環境などの IaC に組み込みやすくなります。writer インスタンスの扱いに独特の手順があるため、事前に確認しておくと安心です。

**リンク**: [Aurora PostgreSQL のエクスプレス構成を CloudFormation で試してみた](https://dev.classmethod.jp/articles/aurora-postgresql-express-cloudformation/)

### Amazon FSx for Lustre Intelligent-Tiering の最低料金が低下

**要約**: Amazon FSx for Lustre の Intelligent-Tiering が、月額およそ760 USD から始められるようになりました（最小料金が4分の1に低下）。

**影響**: HPC や機械学習のワークロードで、小規模から試しやすくなります。コスト面の検討ハードルが下がります。

**リンク**: [Amazon FSx for Lustre のインテリジェント階層化ストレージクラスの最小料金が 4 分の 1 に下がりました](https://dev.classmethod.jp/articles/amazon-fsx-lustre-intelligent-tiering-lower-entry-cost/)
